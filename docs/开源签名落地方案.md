# 免费开源签名落地方案

2026-11-12：用户已选择 SignPath Foundation 免费开源路线。当前仍没有可用 Windows 代码签名证书，未提交申请、未获准、未签署公开发布包。Android 继续使用原发布签名，这与 Windows Authenticode 是两件事。

已只读核对 [Foundation 条件](https://signpath.org/terms)、[申请入口](https://signpath.org/apply)和[GitHub 可信构建接入](https://docs.signpath.io/trusted-build-systems/github)。条件包括 OSI 开源、无不允许的私有组件、持续维护、已经公开发布、可核查的项目声誉和构建来源，以及每次发布人工批准。选择免费路线不等于已经具备资格，也不能保证受理时间或通过。

## 当前实缺材料

- 本地 Git 没有配置远程仓库，也没有可用 GitHub CLI 登录；需要实际 GitHub 项目/账号、维护者名称和联系邮箱。不能把本机路径、假的账号、示例域名或虚构身份作为申请资料。
- 主项目根许可证与著作权声明仍需维护者确认。已有 Moonlight/Sunshine GPL、Tailscale BSD、VDD MIT 等上游材料不等于自有代码已获得开源授权。建议按 GPL-3.0 组合分发审阅，但本轮不擅自授予不可撤回的公开许可。
- 公开发布页、说明文档、维护记录、可信 CI 和批准角色尚未落地。Windows 内测未签包可作为已有本地构建证据，不能代替公开发布历史。
- 修改版 Sunshine 不能直接套用本项目证书。Foundation 对签修改版上游有明确的公开 fork、分支和上游签名条件；目前只准备签自有四个入口，第三方保留原签名与许可。

## 已准备的具体交付

`scripts/Prepare-OpenSourceSigning.ps1` 生成新的本机待审目录：`application-draft.md`、`application-readiness.json`和本方案。草稿附实际版本、允许签名的自有程序、工程材料哈希、已核实官方链接及缺项；不会创建账号、发布代码、替用户填写身份或提交表单。

示例命令（不填身份也能先生成诚实的缺项草稿）：

```powershell
./scripts/Prepare-OpenSourceSigning.ps1 -SourceRoot <整合后的产品源码> -OutputRoot <新的待审目录>
```

得到真实资料后补 `-ProjectUrl`、`-MaintainerName`、`-MaintainerEmail`；维护者确认主项目许可并添加真实根 LICENSE 后，再补 `-LicenseSpdxId`。工具不会因为参数齐全就宣称 Foundation 资格通过，公开/CI/申请审核仍须真实完成。

工程已支持证书存储和外部签名服务两种构建接入，见[签名与更新接入](签名与更新接入.md)。签名顺序必须是自有主程序/后台/卸载器 → 组件哈希与载荷 → 安装器，签后再验可信链、时间戳和固定发布者。不能只给最终安装器补签，却让内含自有程序仍未签。

已核实官方 GitHub Action `SignPath/github-action-submit-signing-request` 的实际输入和源码版本：`2290a7b806cc1cfa69cdc6eec875e730554c6ab1`。输入包括 `api-token`、`organization-id`、`project-slug`、`signing-policy-slug`、`github-artifact-id` 和 `output-artifact-directory`。当前不是已运行 CI；服务项目、策略、凭据和发布者指纹须来自实际获准账号，不能从签名回复自动信任新发布者。

## 公开与申请的实际顺序

1. 准备并审阅只包含 StreamHub 产品的源码导出。公开仓库绝不能直接推送整个“aa杂项”工作区；排除设备证据、用户桌面截图、绑定/账号数据、测试密钥、Android 发布私钥、证书密码和本机应用数据。
2. 由维护者确认真实身份、项目归属和根许可证；保留所有上游许可证、源码、补丁、哈希及必要声明。
3. 建立真实公开仓库/发布页和可信 CI，核对产物来源。每次签名使用指定提交、固定依赖和人工批准；不对任意外部上传文件签名，不在不受信 PR 中暴露凭据。
4. 使用待审草稿在官方入口申请。申请表、公开许可与发布操作须基于真实维护者资料；本轮尚缺这些资料，未提交。
5. 获批后接入实际 SignPath 项目/策略及凭据，签自有程序并核验。随后把真实发布者 SHA256 写入客户端信任根并重新构建。已有143及本轮144无该信任根，首次接入仍需手动安装。
6. 对新签包做定向验收，再接真实 HTTPS 更新源和独立清单密钥。代码签名通过不自动等于自动更新上线；既有 stable 构建和更新安装拒绝条件继续保留。
