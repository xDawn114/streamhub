## 检查和响应

维护者应至少每周及每次发布前核对上述来源；收到可信安全报告或高影响公告时立即补做。记录每条检查的 UTC 时间、检查人、公告编号/URL、实际锁定版本与是否受影响、判断依据、处置与验证证据。尚未检查就写“未检查”，证据不足写“未知”，不要预填“通过”。

确认受影响时，先按远程可达性、是否需要绑定/本地权限、服务权限和敏感数据影响分级；有修复则更新上游与本地补丁、完整源码、哈希锁、许可和构建输入。有必要时停止分发或临时关闭受影响功能。第三方二进制/AAR 变更须重新构建并做对应功能验收；不为消除告警而只改版本文本、删除告警或放松哈希/签名验证。

一条实际跟踪记录至少包含：`component`、`checkedAtUtc`、`checker`、`advisory`、`pinnedVersionOrCommit`、`affected = yes/no/unknown`、`evidence`、`action`、`fixedArtifactSha256`（有新构建时）。此处不提供虚构的已完成记录。

## 一次构建应能追到什么

发布前将以下材料与同一构建号关联保存，敏感文件不进入公开源码包：

1. 自有源码提交、是否有未提交差异及差异哈希；覆盖层合成输入、逐文件源码清单/归档哈希、完整构建命令。仅记录父仓库 HEAD 而遗漏覆盖层差异不够。
2. 第三方上游提交/tag、子模块与外部归档版本/URL/哈希、应用补丁及修改后的文件哈希、许可证和完整相应源码。不要把上游 tag 或下载地址当成不可变内容证明。
3. OS/架构、SDK/运行时、编译器、NDK/JDK/Go/Gradle/CMake/Ninja、runner 镜像与 Action 完整提交、构建参数、依赖解析记录和锁文件。工具链未固定时如实记录，不能宣称位级一致。
4. 产物文件名/大小/SHA-256、产品版本与渠道、内嵌载荷清单、Android 签名证书或 Windows 发布者/时间戳的公开验证信息；签名前后哈希分别关联。私钥、token 和证书密码永不公开。
5. 真实构建/检查日志与批准记录；未跑的扫描、未安装的候选、尚未签名的包分别明确标注。与包同源的哈希清单不能单独认证发布者；还需受信来源和签名链。

`Export-ProductSource.ps1` 只生成可逐字节核对的本机源码导出与清单，**不生成构建来源认证、不证明它对应某个安装包，也不建立签名信任**。公开源码与已知哈希是追溯材料；只有在独立环境重建、比较产物并解释所有差异之后，才可以宣称达到相应程度的可复现构建。当前没有完成这一证明。
