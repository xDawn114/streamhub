# 远程协助（设计草稿）

2026-11-19。本文保留原始设计，并补记本机183分支的实施决定。用户已选择“观看与控制都做，控制须被控端每次亲选”。实现和隔离检查不等于真机验收；九项真机清单仍需逐项取得证据。

## 已定的五项决定

1. v1同时提供仅观看和允许控制。界面不预选模式；允许控制需被控端每次亲选，并二次确认。协助端没有升级权限的接口。
2. 两端显示相同的八位核对号，与本次会话ID、临时证书及凭据绑定。八位协助码只兑换待确认，不是长期授权。
3. 每台被控电脑同时最多一个临时协助，包括待确认和待清理状态。开启前要求已有主/副屏会话结束；协助期间拒绝信任设备串流准备，不能抢占。
4. 协助端无需账号登录。连接信息携带显式地址和固定TLS指纹，需由被控端复制；八位协助码另行提供。没有“只输ID即可跨网”的暗示。
5. 界面文案：“仅支持局域网或已连通的 Tailscale，不提供公网寻址和中继。”

## 本机实现选择

- 候选版本0.8.41/183，独立分支`codex/remote-assistance-183`；182/fix145冻结包、源码标签和已安装程序不动。本轮不打包、安装或公开发布。
- 被控端使用独立`assistance/media`状态和本次证书，复用既有原生引擎及已受防火墙管理的主屏端口；先停空闲主屏再使用端口。不会复制、清空或改写信任设备的媒体库。
- 仅观看通过被控端原生配置禁用键盘、鼠标和触控，手柄在所有临时模式下禁用。没有文件、剪贴板、自动登录或无人值守授权；协助凭据不进入设备库，也不能使用正式设备HTTP接口。
- 10分钟协助码、90秒待确认、25秒心跳宽限、最长2小时会话。正常退出和超时先撤凭据，再停引擎，按会话ID与完整公开证书精确删除并回读。持久恢复记录在媒体变更前落盘；重启一律清理，绝不恢复会话授权。失败每3秒重试，清理完成前阻挡新协助。
- 服务拥有不自动隐藏的被控横幅；横幅无法启动或退出时结束协助。横幅可断开会话，后台崩溃时Windows Job对象结束媒体进程。
- Windows协助端使用固定版本Moonlight Qt接收器。每次生成独立证书和私有便携目录；绑定进程Job，在退出时清除，崩溃后下次启动清扫。不会复用用户已有Moonlight设置。
- 临时接收器禁用自动设备发现。其证书使用会话独有CN；除便携目录外，收尾也按确切名称删除Qt Schannel可能导入的Windows CNG私钥。结束通知与本机清理分别处理，通知失败会显示提示。
- 本机真实接收器握手检查尚未通过：当前进程环境在导入临时私钥时返回`NTE_PERM (0x80090010)`。尚未出画，不能据隔离状态机检查宣称协助已经可用；该问题连同九项真机验收一起列为候选交付门槛。
- 本机源码检查通过不等于真实出画、只读丢输入或断电清扫已证明。应在两个隔离Windows测试端完成下方九项，才进入183候选交付。

## 目标与非目标

**v1 目标**：被控端生成一次性协助码，协助端输入后，由被控端选择"仅观看"或"允许控制"建立会话；会话结束不留下设备绑定。

**v1 不做**：跨网寻址与中继（需要独立项目，涉及服务器与带宽）、文件/剪贴板/自动登录、多协助端并发、协助端反向控制被控端。

跨网这条要写进界面文案：**v1 只复用局域网或已连通的异地通道，协助码管"谁能连"，不管"网络通不通"。**

## 两种授权

| | 信任设备 | 临时协助 |
| --- | --- | --- |
| 身份来源 | 已绑定的设备凭据（复用现有独立设备授权） | 一次性协助码兑换出的临时会话凭据 |
| 存活期 | 长期，按设备撤销 | 会话期间，结束即回收 |
| 是否写入设备库 | 是 | **否**，不得登记成一台设备 |
| 无人值守 | 可选，单独开关 | 不适用（必须本机确认） |

两者共用同一套会话与权限接口，差别只在"身份从哪来"和"活多久"。

## 协助码

- 格式 8 位字母数字，分两组（如 `7F3K-92QX`），**与现有六位绑定短码在视觉上必须能区分**，否则用户分不清哪个该念给谁。
- 由被控端生成，绑定：会话 ID + 生成时刻 + 一次性 nonce。
- 限时 10 分钟、单次使用、输错 5 次作废，每次尝试记录来源与结果。
- **码本身不授信**：兑换后只得到"待确认"状态，必须由被控端点选模式才建立会话。

## 会话凭据

- 兑换出的凭据一次性、与会话同寿命，**不写入设备授权库**。
- 复用的是权限作用域模型，不是设备身份模型：协助端不是"一台已绑定设备"。
- 会话结束、被控端取消、超时，三种情况都要让凭据立即失效。

## "仅观看"在哪一层强制

- **被控端丢弃输入事件**（键盘/鼠标/触控），客户端隐藏 UI 不算数——改过的客户端照样能发输入。
- 会话中不允许协助端自己请求升级为"允许控制"；要升级必须由被控端重新确认。
- 审计记录写入实际模式，事后可查。

## 收尾与清理

这里是整个功能最容易被绕过的地方，现有文档写明撤权后的媒体证书清理与崩溃恢复"仍待实机证明"。

- 正常结束：结束会话 → 回收凭据 → 清理 media 配对 → 回读确认清理完成。
- 异常结束（被控端崩溃/断电）：启动时清扫带"协助会话"标记且未完成的配对，按会话 ID 精确删除，**不按设备名猜测**。
- 清理失败：进入待重试队列，并且在清理成功前拒绝新的协助会话。

## 被控端提示

- 会话期间常驻横幅：谁在连、什么模式、断开按钮。
- 协助会话不自动收起（与信任设备的 5 秒收起不同）。
- 首次使用前一次性说明"能看到什么、不能做什么"。

## UI 落点

- 侧栏"远程协助"只处理临时会话；"全部设备"继续只管长期绑定。不在顶栏再加一份入口。
- 协助端：输入码 → 等待被控端确认 → 会话。等待态要能取消。

## 验收清单（真机，缺一不可）

1. 协助码输错 5 次作废；2. 过期码不可兑换；3. 仅观看下真实输入无效；4. 被控端确认界面必须点到；5. 结束 30 秒内配对清理完成（回读）；6. 被控端强杀重启后清扫掉残留配对；7. 设备列表不新增条目；8. 横幅常驻且可一键断开；9. 协助会话进行中信任设备连接的行为符合预期。

## 原待定问题（决定见文首）

1. v1 是否开放"允许控制"，还是先只做"仅观看"。
2. 协助码要不要两端显示同一个号码（防"你念给我听"的串话）。
3. 同一台被控端同时允许几个协助会话（建议 1）。
4. 协助端是否要求登录（建议 v1 不要求）。
5. 跨网不支持这件事，在界面上用一句话怎么说。

## 主要风险

**诈骗利用**是这类功能的首要风险。三道防线：必须本机确认、常驻横幅、v1 不给文件/剪贴板/自动登录。技术上怎么加固都替代不了"被控端有人看着"。

## 冻结记录（2026-11-20）

用户决定冻结 Windows 对 Windows 远程协助：暂停新增功能、界面调整、性能调优和专项测试，待明确要求后恢复。源码、安装状态与入口保留，不卸载、不重打包。

**一次真实两机实测（朋友电脑）结果**：接通并出画，首帧体验尚可；持续操作明显卡顿、画质模糊；系统级快捷键无法触发。未采集帧率、码率、网络指标，因此**不判断根因、不记作验收通过**。

**恢复时按这个顺序查**（先测数据，再改代码）：

1. **主机端有没有用上硬件编码**。同时出现"卡 + 模糊"，最常见就是退回软件编码。先看被控端是 Intel 核显、AMD 还是独显，编码器实际选中的是哪个，是不是回退了。
2. **码率与预设**对这台机器和这条网络是否过低。模糊通常先于卡顿出现，但两者同时出现更可能是码率被压或编码跟不上。
3. **链路**：Wi-Fi 还是有线、实际吞吐和丢包。这次没采网络指标，等于这一层完全空白。
4. **快捷键**单独看：系统级组合（Win、Alt+Tab、Ctrl+Alt+Del）在很多串流客户端里本来就是限制，不一定是性能问题。要让产品明确写出支持哪些组合，而不是事后当 bug。

**这条记录的价值**：单机回环测试跑了很久没发现的问题，两机实测二十分钟就暴露了三个。恢复后第一件事应该是补采一段带指标的两机数据，而不是直接改代码。
