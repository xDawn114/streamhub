## 接入步骤

1. 取得真实代码签名资格与私钥访问条件。在 Windows SDK 安装 signtool。构建脚本的 WindowsSigningCertificateThumbprint、WindowsSigningCertificateStore、SignToolPath 接入现有证书存储或硬件密钥；脚本不导出私钥。先签自有主程序、服务、卸载器，再生成组件哈希和嵌入载荷，最后签安装包并核验可信时间戳。正式 stable 构建缺证书直接失败。
2. 保留 Sunshine、Tailscale、Wintun、VDD 的来源和现有原厂签名。项目证书只签自有入口；对自行修改的 Sunshine 二进制另核对签名服务规则及上游归属，不擅自重签第三方程序。
3. 更新清单使用独立 RSA 3072 位以上的 SHA256/PSS 密钥。只把公钥 SPKI Base64、真实安装包签名证书 SHA256 和 HTTPS feed 写入 common/Updates/update-trust.json 并重新构建。私钥置于源码/发布目录外的受控签名环境，不随包分发。
4. 用 Create-UpdateManifest.ps1 生成具有版本、渠道、架构、最低安装版本、有效期、大小、哈希的签名清单。安装包和 feed 必须同一 HTTPS 来源。清单生成器拒绝未受信签名或非白名单发布者。清单签名与 Authenticode 是两次独立验证。
5. 更新器只接受构建时固定的信任根，不从 feed 获取新密钥；不跟随重定向，不允许降版或跨渠道，大小/哈希/签名/发布者任一不符都停止。安装前再次锁定文件并重新校验，等待用户完成 UAC。当前未实现绕过 UAC 的无人值守更新。
6. 安装器通过本地已认证 IPC 进入两分钟维护窗口：无正在准备/串流的会话、无文件请求时才允许，之后暂停新会话和新文件请求。服务实际停止前再次获得维护锁，安装失败恢复备份。界面“恢复上个版本”调用产品卸载器的 --rollback，先核对受保护的备份全文件哈希，再恢复程序；绑定及个人设置保留。旧130版不支持维护窗口，首次迁移仍使用人工安装，131起才能使用此更新协议。
