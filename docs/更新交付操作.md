# 更新交付操作：本机准备、真实接入与首次升级

阶段80在0.8.9/141补齐本机发布目录、核对工具、签名服务适配及安装后结果反馈。没有真实证书、站点或清单密钥，因此当前包仍未开启线上更新；本文件不表示已经申请、签名或上传。

## 先提供的四项资源

1. 可直接返回静态文件的真实HTTPS站点与维护权限。双端清单和安装包同源、无登录、无跳转；清单不长缓存，安装包按哈希不可变保存。不需要另建账号服务器。
2. 发布清单独立RSA3072或以上的签名密钥。私钥在源码、候选包和上传目录外，由发布者保管；这里只内置对应SPKI公钥。本轮没有生成生产私钥。
3. Windows受信代码签名证书，或已获批的签名服务及真实发布者证书SHA256。签名与SmartScreen信誉不是一回事，签名不保证没有信誉提示。无证书时可以显式准备Windows仅查询清单，但不能下载/安装未签名更新。
4. 原Android发布签名。现有证书SHA256为`A5A93959BDE9B991A6773DC9E197EB105320E0826889D902E7890FE1BDFD4F6C`，更新沿用，不新建包名或替换密钥。

维护者、公开仓库、项目许可证与CI等签名资格材料见[签名申请材料](签名申请材料.md)。站点、密钥访问和申请主体由项目方决定，本轮不注册服务、不购买证书、不提交申请。`deployment/update-publication-inputs.template.json`用于收集非秘密配置，不存私钥或访问令牌。

## 先配置，再构建

在合并好的源码快照上运行`Configure-UpdateTrust.ps1`，填真实双端feed、SPKI公钥和Windows发布者指纹。`Test-UpdateReadiness.ps1 -RequireQueryReady`只做本机预检，格式就绪不代表域名归属、站点可达或签名已受信。

配置改变后必须重新构建双端，不能只改服务器文件；发布准备脚本会核对候选源码归档中的信任配置。以后换公钥/域名也要提前随受信版本分发，更新服务器不能自行替换客户端信任根。

Windows构建支持二选一：

- 证书存储：`构建电脑端.ps1 -WindowsSigningCertificateThumbprint <SHA1> -SignToolPath <signtool.exe> ...`，沿用既有验证。
- 已授权签名服务：`构建电脑端.ps1 -WindowsSigningScript <源码之外的本机适配器.ps1> ...`。适配器契约为`param([string[]]$Files)`，对这批自有程序原位签名；先处理主程序/服务/卸载器，再生成载荷，最后签安装器。适配器的账号、网络提交及服务批准由发布者配置，仓库不携带凭据，不自动提交第三方服务。返回后再次验证系统信任、时间戳和内置发布者指纹，不能凭exit0放行；stable仍禁止无签名构建。

第三方组件的原厂签名、来源与许可保持原样。签名适配器不进入源码归档，只允许指定自有入口，不能拿它批量重签第三方程序。

## 本机交付目录

先运行`Prepare-UpdatePublication.ps1 -CandidateRoot <配对候选根> -OutputRoot <新目录> -Mode Plan -SourceRoot <构建源码快照>`。Plan核对双端包/源码版本和哈希，输出缺项，不联网、不签名、不生成密钥。

资源齐全后用同一工具`-Mode Stage`，补`-ManifestPrivateKey <外部PEM路径> -NotesFile <更新说明> -AndroidCertificateSha256 <原证书指纹>`。默认Windows必须有可信签名；仅版本提示须明确`-WindowsQueryOnly`，且客户端发布者白名单必须为空。无法因此跳过客户端安装校验。

Stage完成后才生成`ready/`：

```
ready/publication.json                  # 双端版本、revision、包/清单哈希与发布顺序
ready/site/<实际Windows清单路径>
ready/site/<实际Android清单路径>
ready/site/packages/<渠道>/<版本-构建码>/<包哈希>/windows.exe
ready/site/packages/<渠道>/<版本-构建码>/<包哈希>/android.apk
```

新目录不能覆盖旧待审目录。中断或失败只留下`staging-*`供排查，不生成`ready`。私钥不得位于源码、冻结候选或交付输出中，不会复制到site。脚本没有上传功能。

`Test-UpdatePublication.ps1 -PublicationRoot <ready> -SourceRoot <源码快照>`独立重验实际包字节、两份清单签名、版本、有效期及同源关系。所有文件完整后才能人工审核部署。

## 上传和回退顺序

先上传全部`packages/`不可变文件，再逐份原子替换清单。清单短时间一端先更新并不造成跨端强制升级，两个客户端各自验证；不能覆盖旧哈希路径里的包。参考`deployment/nginx-update-site.conf.template`设置只读静态站点、HTTPS和缓存头；模板需部署方填写，不会修改开发机网络或服务器。

部署后明确加`Test-UpdatePublication.ps1 -Online ...`才访问真实站点，以禁止跳转的GET核对线上清单与包的完整字节、大小、哈希及清单缓存头。这个只读检查仍不能代替客户端升级、UAC/安卓确认或回滚验收。

服务器侧回退先恢复仍在有效期内的已审清单，保留已上传包；客户端不接受降版，所以已升级用户需Windows本机“恢复上个版本”或发布更高构建码的修复版。Android不提供安装后自动降级，失败/取消保留当前应用，不能称作完整回滚。

## 首次上线与明天验收

当前已装140没有更新源或公钥，不能靠一次服务器配置自行获得在线更新能力；141当前本机候选也保留空信任根。因此拿到资源后，**首个带真实配置和可信签名的版本需手动覆盖安装一次**，之后再从该版本验证后续在线更新。不要为演示写入临时域名或测试公钥，也不为当前空配置包反复安装。

明天只在用户安排后安装。普通版先验更新入口与安装结果提示，手机分支另验小屏布局；合并后只补交叉改动。真实发布资源尚缺的线上步骤继续标未测。已经稳定且未改动的串流、文件、剪贴板、音频和隐私不重复全量验证。

安装确认仍由用户操作。Windows记录安装尝试并在重启后根据实际构建码确认；旧码仍在时提示未确认完成，可重试。Android同样以新进程的实际构建码确认；打开系统安装页不是成功，取消或中断不会显示“更新完成”。下载始终重新验签、安装前重新核对空闲及包完整性。
